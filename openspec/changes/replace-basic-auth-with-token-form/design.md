# Design

## Context

See proposal.md — Why for motivation.

What shapes the approach:

- The session is already the LiveView authority. `on_mount` reads only
  `session[:dashboard_authenticated]` and never re-checks the token, so the cookie is
  already the entire post-login trust surface. This change moves HTTP into agreement
  with that rather than introducing a second mechanism.
- The session is a **signed, not encrypted**, `:cookie` store (`store: :cookie`,
  `signing_salt: "AgFsn3Bi"`, `same_site: "Lax"`, no `max_age` configured). Whoever
  holds the cookie is authenticated. That is tolerable for a boolean; it is why the
  session must not store the token itself.
- The auth plug sits **before** `put_root_layout` and `protect_from_forgery` in the
  `:browser` pipeline, and halts with `send_resp/3`. A redirected response therefore
  cannot currently carry the root layout, and no CSRF token has been generated by the
  time the plug runs.
- `use LoggerDashboardWeb, :live_view` injects `on_mount` **globally**. A login page
  built as a LiveView would be gated by its own hook and redirect to itself. The token
  page therefore cannot be a LiveView unless that hook moves to a per-`live_session`
  scope — which is a bigger change than the page needs.
- `CoreComponents` already supports `type="password"` in `<.input>` and renders daisyUI
  classes; `<.button>` defaults to `type="submit"`. No new UI primitive is needed.
- `Layouts.app/1` requires `flash` and renders nav links to all four gated routes, so it
  is wrong for the token page — but right for the sign-out control.
- `conn_case.ex` puts an `Authorization: Bearer` header on every conn it hands to eight
  test files, and mutates global app env while doing so.
- The archived `2026-10-02-add-containerfile-basic-auth` change rejected this exact
  design in writing. Its stated blockers are now all present in the codebase.

## Goals / Non-Goals

**Goals:**

- One credential mechanism: the session cookie. No `Authorization` header path at all.
- The token page is a real page — real layout, real form, real CSRF — because it is the
  only page an unauthenticated operator ever sees.
- A session cannot outlive the token that created it, so rotating the token is a real
  revocation.
- Keep `DashboardAuth` as the token's owner. It already has `valid?/1`,
  `get_token/0`, and `generate_token/1`, and all three are what this needs.

**Non-Goals:**

- User accounts, usernames, or any per-identity notion. There is one shared token and
  that stays true.
- Per-user sessions, session listings, "sign out everywhere", or an audit of who
  signed in. There is no identity to audit.
- Multiple simultaneous tokens. One valid token, as today.
- Rate limiting or lockout on repeated wrong tokens. Deliberately out of scope: the
  token is 256 bits, so guessing is hopeless and the form is not the weak link.
- Making the token page a LiveView, or moving `on_mount` into `live_session` scopes.
- Encrypting the session cookie. It will not hold a secret after this change.
- Anything about `force_ssl`, TLS termination, or the existing "serve over TLS"
  warning. Unchanged.

## Decisions

### D1: A controller-rendered token page, not a LiveView

`AuthSessionController` renders a `GET /login` page and handles a `POST /login`. The
page is a plain template under the shared root layout, using `<Layouts.app>`'s siblings
directly rather than `Layouts.app` — no nav, no flash group, since neither belongs on a
page with no session.

The form posts to the same route with Phoenix's `<.form>`, which emits the CSRF hidden
field, and `protect_from_forgery` in the public pipeline validates it. This is the same
CSRF story the four existing LiveView forms already have, reached over HTTP instead of
the socket.

*Alternative considered*: a LiveView login page, with `on_mount` moved out of
`use LoggerDashboardWeb, :live_view` into per-`live_session` hooks. Rejected — it is a
structural change to every LiveView in the app to obtain something a controller and a
template already give, and it would leave the login page itself depending on the gate it
is supposed to replace.

*Alternative considered*: Phoenix's `AuthController` macro (`use Phoenix.Controller,
layouts: [...]`). Rejected — it brings its own session keys, its own failure routing, and
its own logout route, none of which match the token-binding this needs.

### D2: The session records a digest, not a boolean and not the token

`DashboardAuth.digest/0` returns `:crypto.hash(:sha256, get_token())` as lowercase hex.
The session holds that digest. Every gate compares the session's digest against the
current one with `Plug.Crypto.secure_compare/2`.

Three properties fall out. The cookie, which is readable by anyone who has it, contains
no usable secret — it is a digest, and reversing it means guessing the 256-bit token. A
rotated token no longer matches, so outstanding sessions end, which makes
`compose down && up` with an ephemeral token a real revocation rather than a cosmetic
one. And the comparison stays constant-time, because the digests are fixed width and
`secure_compare/2` requires that.

The digest is recomputed per request from `get_token/0` rather than cached, so a token
change takes effect without restarting the gate.

*Alternative considered*: keep the boolean and store the token's generation timestamp.
Rejected — a timestamp is not a secret to compare, and it adds a second source of truth
about when the token last changed.

*Alternative considered*: keep the boolean as today. Rejected — that is the behaviour
this change exists partly to remove; a copied cookie would outlive the token.

### D3: A second pipeline, and the gate runs *before* `:accepts`

The token page cannot share a pipeline with the routes it protects, so there are two:

```
:browser_unauthenticated -> BrowserSession, fetch_live_flash, accepts ["html"]
:browser                 -> BrowserSession, DashboardAuth, accepts ["html"], fetch_live_flash
```

`Plugs.BrowserSession` holds the four plugs both share — `fetch_session`,
`put_root_layout`, `protect_from_forgery`, `put_secure_browser_headers`. Phoenix
pipelines cannot extend one another (`pipe_through/2` is for scopes, not pipelines), so
without this module the list would be duplicated and a drift would mean the token page
quietly losing CSRF protection with nothing failing until it mattered.

**The gate's position is the opposite of what this document originally said.** It was
going to move *below* `put_root_layout` and `protect_from_forgery`, on the reasoning
that a redirect must be able to render a page. It does not: the gate only ever
*sends a redirect*, and the token page is a separate request that reaches the router on
its own and gets the root layout there. So the gate needs nothing but `fetch_session`
before it.

What it does need is to sit *before* `:accepts`. It answers a request by asking whether
the client accepts HTML, and `:accepts ["html"]` answers that by raising `406 Not
Acceptable` first — telling a script the dashboard cannot produce JSON, which is true
and useless. Behind the gate, `:accepts` still governs what an authenticated request may
render. Getting this backwards is the one thing in the router that would quietly delete
the `401` branch the spec requires.

`fetch_live_flash` is in the public pipeline because a successful sign-in sets a flash
the *next* page reads, and `put_flash/3` refuses without it. The token page itself
renders no flash group, which is why signing out sets no flash either: nothing would
display it, and it would misattribute itself to the page after the next sign-in.

### D4: `on_mount` redirects to the token page and verifies the digest

`on_mount(:default, ...)` recomputes the digest, compares it against the session, and
either continues or halts with `redirect(socket, to: ~p"/login")`. Today's
`to: "/"` is replaced, because `/` is itself gated and would bounce the socket to a
redirect that the mount hook then has to chase.

The dead `on_mount(:ensure_authenticated, ...)` clause is removed: it exists only for a
test, it forwards to `:default`, and `:default` is what `use LoggerDashboardWeb,
:live_view` actually expands to.

*Why the digest is re-checked on mount at all*: the socket bypasses router plugs after
the upgrade, so the mount hook is the only place a stale cookie is caught mid-session —
which is exactly the case a token rotation creates.

### D5: One credential path means `DashboardAuth` loses its header parsing

`extract_token/1` and `authenticated?/1` are deleted along with the `Basic` and `Bearer`
clauses of `parse_authorization/1`. `valid?/1`, `get_token/0`, `generate_token/1`,
`resolve_token/1`, `generated?/0`, and `announce_boot_token/0` are unchanged.

`valid?/1` is already exactly what a form POST needs: conn-free, constant-time, fails
closed when no token is configured, and returns `false` for a non-binary. Keeping it
means the comparison path is the one already covered by
`test/logger_dashboard/dashboard_auth_test.exs`.

Deleting the header parsing rather than leaving it unused is the point of "remove both
header schemes": an authentication path nobody exercises is one that can silently
regress and nobody notices.

### D6: Sign-out is a controller action that deletes the session

`DELETE /logout` clears the session and redirects to the token page. It is a
controller, not a LiveView event, so it cannot be reached by a stale socket and does not
need to be re-authenticated first — signing out must work precisely when the session is
no longer trusted.

The control in the shell is a plain form-post link rather than a `phx-click`, for the
same reason the token form is HTTP: it has to work with no valid LiveView connection,
which is the state an operator is in when they want to sign out.

### D7: The session gets an explicit `max_age`

`@session_options` currently sets no `max_age`, so the cookie follows `Plug.Session`
defaults. A session that is bound to a token does not need a short life for security —
rotation handles revocation — but it should have a *stated* one rather than an inherited
default nobody chose. Eight hours is long enough to cover an incident and short enough
that an unattended browser forgets.

*Alternative considered*: leave it defaulted. Rejected — the default is invisible and
this change is the moment to make the session's lifetime an explicit decision rather
than an accident.

### D8: `conn_case.ex` logs in through the token page

The shared test setup stops injecting an `Authorization` header. It posts to
`/login` with the configured token and keeps the resulting session cookie.

This is the single place that changes for eight test files, which is the reason the
header path had to be removed rather than merely discouraged — leaving it would mean
every test kept depending on the mechanism this change deletes.

Three helpers came out of writing it, and they are not all the same thing:

- `sign_in/2` posts the form. The default, because the form is the mechanism under test
  and a harness that skipped it would leave the one path an operator actually takes
  untested.
- `authenticate/2` writes the digest into a test session directly, for asserting what a
  *stale* session does — a rotation test must be able to hold a cookie the current token
  no longer matches.
- `unauthenticated/1` for asserting the gate refuses.

One trap, worth recording because it cost time and would cost it again: `Plug.Test`
conns hand a LiveView mount a bare session map, and a cookie round trip has stringified
its keys by then. `Plug.Conn.get_session/2` normalises an atom key, so the plug half
looks fine; `on_mount` doing `session[:dashboard_auth_digest]` finds nothing and turns
every authenticated socket into a redirect loop with nothing in the logs. Both read
paths go through one helper that accepts either form.

*Alternative considered*: keep `init_test_session` writing the digest directly, with no
login request. Rejected — it would bypass the form the change is about, and no test
would exercise the path an operator actually takes.

## Risks / Trade-offs

- **Removing the header path breaks scripted access.** Anything using
  `curl -H "Authorization: Bearer …"` or `curl -u operator:…` stops working, with no
  deprecation warning, because the token is now only accepted from the form.
  → Documented as a breaking change in the README with a login-then-use recipe. This is
  the agreed cost of a single credential path; the alternative was two mechanisms to
  keep testing.

- **The default ephemeral token signs everyone out on every restart.** Binding the
  session to the token means a container restart with no `DASHBOARD_AUTH_TOKEN`
  invalidates every open session.
  → Accepted deliberately: the token rotated, so the sessions were established under a
  secret that no longer exists. The README already tells operators the ephemeral token
  "changes on every restart"; this makes that visible in the UI. Operators who want
  sessions to survive set a pinned token, which the compose stack already requires.

- **A cookie is a bearer credential.** Anyone who copies it is authenticated for its
  remaining life; there is no per-request proof and no client certificate.
  → Bounded by D2 (no secret in the cookie), D7 (bounded lifetime), and the existing
  `force_ssl` in prod, which is what makes a cookie safe to issue at all. The previous
  `Authorization` header had the same property for the same duration, so this is not a
  new exposure — it is the same one in a different container.

- **The token page is unauthenticated surface.** It is now the only thing an
  unauthenticated request can reach, so it must not leak: the field is `type="password"`,
  the submitted value is never echoed back, and errors name neither token.
  → Specified and tested as its own requirement rather than left to the template.

- **The plug no longer answers `401` for browsers, so any monitoring watching for
  `401` from `/logs` goes quiet.** The health checks in `Containerfile` and
  `compose.yaml` accept `^(200|401)$` and would now see `302`.
  → Updated to accept `302`, in the same change, in both places.

- **No rate limiting on the token page.** Unlimited wrong-token attempts against a
  256-bit secret is not a practical attack, but it is unbounded log-free request volume.
  → Accepted for now; noted as the thing to add if the dashboard is ever exposed beyond
  loopback, where `force_ssl` and the loopback-only port binding stop being free.

## Migration Plan

1. Land `DashboardAuth.digest/0`, the new controller and template, the new pipelines,
   the rewritten plug, and the sign-out control. `conn_case.ex` changes in the same
   commit, because the old setup depends on the header path being removed.
2. Update both health checks to accept `302` in the same change — otherwise the compose
   stack reports the dashboard unhealthy from the moment it deploys.
3. Rewrite the README authentication section: replace the two `curl` recipes with
   login-then-use, and replace the "browser gets a 401 prompt" paragraph with the form's
   behaviour.
4. Rollback is a previous image. No stored data, migration, or configuration changes, and
   the session cookie is simply ignored by a release that reads the header instead.
5. Deploying this invalidates every existing session, because no existing cookie carries
   a digest. That is the intended outcome, not a migration step.

## Open Questions

None. Header survival, redirect shape, session binding, and sign-out were each settled
before the specs were written, and each is pinned by a requirement in
`specs/dashboard-auth/spec.md` and `specs/dashboard-shell/spec.md`.
